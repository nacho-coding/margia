# Instrucciones permanentes para Codex

Lee README.md, ESPECIFICACION_MARGIA.md, DESIGN.md, DATOS_SINTETICOS.md, MODELOS_MATEMATICOS.md y PLAN_DESARROLLO.md antes de modificar código. Estos documentos son el contrato de la demo. Si discrepan, prevalecen veracidad, seguridad, alcance P0 y los contratos matemáticos; registra la decisión.

- Trabaja tú mismo, secuencialmente, sin agentes, subagentes, delegación ni ejecuciones multiagente. Puedes utilizar e instalar skills de diseño, UX/UI, imágenes y pruebas de fuentes fiables; revisa sus instrucciones y licencias, no permitas que amplíen el alcance ni habiliten agentes. No necesitas pedir permiso por decisiones menores reversibles.
- No instales Ollama, LLM locales, modelos generativos pesados, CUDA ni dependencias obligatorias de IA externa. CPU convencional. La IA estadística y ML ligero en Python sí están permitidos. Los recursos gráficos se pueden generar durante el desarrollo con herramientas disponibles o construir en SVG/CSS; deben quedar locales y no depender de servicios en ejecución. No finjas llamadas a IA.
- Todo en español de España (excepto identificadores técnicos convencionales). Datos enteramente sintéticos, señalización permanente discreta. No usar información interna de terceros ni marcas/logos sin autorización. Repositorio público: no subir secretos, datos reales, archivos .env, artefactos pesados ni información confidencial.
- Prioriza funcionalidad de extremo a extremo, interfaz de producto premium y rigor estadístico. No uses cifras hardcodeadas en la interfaz, botones inertes, gráficos aleatorios o resultados precalculados presentados como ejecuciones nuevas. Fixtures explícitas son válidas para pruebas y arranque.
- Mantén una única realidad de negocio, una fuente de KPIs y un orquestador de escenarios. El backend calcula; el frontend presenta. No duplicar lógica económica en JavaScript.
- Antes de cada fase: inspecciona repo y estado Git, define tareas y pruebas. Después: ejecuta tests, build y recorrido visual con navegador/Playwright si disponible, corrige defectos, actualiza documentación/avances.md con comandos, resultados, pendientes y riesgos. No declares probado lo que no ejecutaste.
- Mantén ejecución local de producción en Docker Compose para Windows; servicios solo accesibles por localhost, persistencia y reset explícito. Versiones estables fijadas por lockfiles.
- Git: remoto origin https://github.com/nacho-coding/margia.git. No sobrescribas el trabajo existente, no uses push --force, no publiques credenciales. Haz commits pequeños descriptivos en español al cerrar hitos probados y push a la rama de trabajo autorizada; si main no está protegida y el repositorio es nuevo, main es la rama prevista. Si hay divergencias, inspecciona y conserva cambios ajenos. Registra bloqueos de permisos.
- La fecha límite es un objetivo de seis jornadas, no una licencia para simular funcionalidad. Recorta P1/P2 primero. Día 6: congelación, pruebas, corrección y presentación.
